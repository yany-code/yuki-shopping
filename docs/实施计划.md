### 结构调整审查结论（2026-09-06）

迁移质量好，可继续推进：`@MapperScan("**.mapper")` 仍匹配、SkuMapper.xml 命名空间已同步、实体注解（`@TableName`/`@Version`/填充）齐全、编译通过、服务实测可启动。

发现的问题（按重要性）：

1. **README「目录约定」过时**：仍写 `modules/*/repository`，实际是 `domain` + `mapper`；且本机 `mvn spring-boot:run` 因 Maven 仓库路径含中文括号会 fork 失败，README 应注明用 `mvn package` + `java -jar` 或 IDE 启动。
2. **启动日志出现 generated security password**：`UserDetailsServiceAutoConfiguration` 未排除，生成无用的内存用户。无功能影响，阶段 1 时用 `spring.autoconfigure.exclude` 排除。
3. **ReviewDTO 位于 product 模块但接口挂在 OrderController**：依赖方向 order→product，与「订单依赖商品」一致，可接受；立规矩：product 不反向依赖其他业务模块，Review/ReviewDTO 留在 product。
4. **数据源事实（2026-09-06 核实）**：3306/6379 实际由 docker-compose 容器 `yuki-mysql`(mysql:8.4)/`yuki-redis`(redis:7.4) 提供（`com.docker.backend.exe` 转发 127.0.0.1），种子数据在 `mysql_data` 卷中实测完好（`yuki@172.18.0.1` 即容器网桥连接）。本机 `MySQL80` Windows 服务已被改到 **3307** 端口（外加 33060 X 协议口），与项目端口完全错开、互不冲突，可忽略或停用。
5. 杂项：compose 字符集 `utf8mb4_unicode_ci` 与 schema 的 `general_ci` 不一致（表级 DDL 优先，无实际影响）；`.env` 按「工作目录」解析，换目录 `java -jar` 会因 `${DB_PASSWORD}` 无默认而启动失败（可接受，知道即可）；openapi.yaml 缺管理端路径、无测试代码（均已列入阶段 7）。

数据库设计要点（实现时必须遵守）：

- 无物理外键，关联完整性由应用层保证；
- 金额一律 DECIMAL，接口层用字符串传输；
- 核心表逻辑删除（`deleted`），订单/明细/评价创建后不可变；
- 订单保存商品、规格、图片、收货地址快照；
- 防超卖靠 `t_sku.stock >= ?` 条件更新 + `stock_version` 乐观锁；
- 唯一约束支撑业务：`uk_user_sku`（加购累加）、`uk_order_item_id`（一明细一评价）、`uk_order_no`/`uk_payment_no`（幂等）。

### 阶段 1：用户与认证（约 1 天，下一步）

实现要点（控制器签名与 DTO 已就位，只写 service 与映射）：

- [ ] `AuthServiceImpl.register`：username/phone 查重（40900）+ `DuplicateKeyException` 兜底 → BCrypt 入库 → 注册即签发 TokenVO（如前端想要 UserVO 需与返回值约定文档一并对齐）
- [ ] `AuthServiceImpl.login`：按 username 查（`deleted=0` + `status=1`，否则 40100）→ `passwordEncoder.matches` 失败统一返回 40100（不区分「用户不存在/密码错」，防用户名探测）→ 签发 TokenVO（expiresIn 用 props 秒数）
- [ ] `AuthServiceImpl.refresh`：`JwtTokenProvider.parse(token, REFRESH)` → 校验 userType=USER → 签发新 access（可选：滚动续期 refresh）
- [ ] Redis refresh token 白名单：`auth:refresh:{userId}` 存当前 refresh token（或 jti），TTL 7d，刷新轮换时更新；为后续登出/撤销留口
- [ ] `GET/PUT /users/me`：UserVO 映射（禁止返回 passwordHash）；改手机号需唯一校验
- [ ] 地址 CRUD：归属校验（user_id 不符统一 40400 或 40300，全项目保持一致）；`isDefault=1` 新增/设默认时事务内清除旧默认；列表默认地址优先

### 阶段 3：购物车（约半天）

- [ ] `POST /cart/items`：同 SKU 已存在则累加数量（依赖 `uk_user_sku`，用 `ON DUPLICATE KEY UPDATE` 或先查后改）；校验 SKU 上架且启用

### 阶段 4：订单与支付（约 2~3 天，核心难点）

**订单创建（事务，对应验收项 2/4）：**
- [ ] `POST /orders/preview`：按地址 + 请求明细试算金额，不扣库存
- [ ] `POST /orders`：Idempotency-Key 幂等（Redis 记录首次结果）→ 地址归属校验 → 查 SKU/商品校验上架 → 条件扣库存（`stock >= quantity`，任一 SKU 失败整单回滚并返回 40900）→ 计算金额（`payAmount = totalAmount + freightAmount - discountAmount`）→ 写订单 + 明细快照 → 删除已结算购物车条目
- [ ] 订单号生成规则（时间戳 + 随机/雪花，满足 `uk_order_no`）

**订单查询与流转（状态机，对应验收项 6）：**
- [ ] `GET /orders`：我的订单分页，按状态筛选
- [ ] `GET /orders/{orderNo}`：详情 = 订单 + 明细快照 + 支付信息，校验归属
- [ ] `POST /orders/{orderNo}/cancel`：仅状态 10，释放库存，写 cancel_time，10→50
- [ ] `POST /orders/{orderNo}/confirm`：仅状态 30，30→40，写 finish_time
- [ ] 状态流转统一封装，非法流转抛 40900，服务端校验不依赖前端

**支付（对应验收项 3）：**
- [ ] `POST /orders/{orderNo}/pay`：仅状态 10；金额从订单读取不接受客户端值；写 `t_payment` 流水返回模拟支付参数
- [ ] `POST /payments/callback`：验签 + 按 `paymentNo` + 金额校验；成功则支付流水置成功、订单 10→20、写 pay_time、累加商品销量；重复成功回调直接返回成功不重复推进（模拟签名规则：`MD5(paymentNo|status|amount|密钥)`，密钥经 `.env` 的 `PAY_SECRET` 注入；重复成功回调一律返回成功，已写入接口文档 3.4）

**回归点**：并发两个请求买最后 1 件只有一单成功；改价后历史订单仍显示快照金额；回调重复投递订单状态不变。

## 五、约定与提醒

- 事务、库存扣减、支付验签一律放 service 层，控制器只做参数校验和编排（README 明确要求）。
- 客户端传入的 userId、价格、库存、金额全部不可信，一律以服务端查询为准。
- 响应不得暴露 `password_hash`、`deleted`、`stock_version` 等内部字段。
- 金额接口层用字符串、库内用 DECIMAL；时间格式 `yyyy-MM-dd HH:mm:ss`。
- 所有资源按当前登录用户的 user_id 做数据隔离。
- 模块依赖方向：`auth/user/cart/order/admin` 可依赖 `product`（商品域是公共下游），**product 不反向依赖其他业务模块**；跨模块复用的实体与 DTO 留在所属模块（Review/ReviewDTO 留在 product）。
- 扁平结构命名：`domain` 包内 entity 用裸名（User/Sku），请求体 `XxxDTO`，响应体 `XxxVO`，查询参数 `XxxQuery`；文件多时可再分 `domain/dto`、`domain/vo`，非必需。
