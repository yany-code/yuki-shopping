# 由岐商城后端实施计划

> 依据：[api接口库.md](api接口库.md)（V1 接口规范）+ [01_schema.sql](01_schema.sql)（13 张表）+ 现有骨架代码盘点。
> 用法：按阶段顺序推进，每完成一项勾一项；每个阶段结束启动服务用真实请求回归一遍，不等最后统一测。
> 盘点日期：2026-09-05

---

## 一、现状盘点

| 部分 | 状态 |
|---|---|
| pom.xml | Java 17 + Spring Boot 3.3.5 + Web/Validation/Security + MyBatis-Plus 3.5.9 + MySQL + Lombok |
| application.yml | 端口 8080，context-path `/api/v1`（与文档一致），MySQL 环境变量注入，Redis 配置存在但依赖未引入 |
| 公共层 | `ApiResponse`/`PageResult`/`BusinessException`/`GlobalExceptionHandler`/`SecurityConfig` 已就位 |
| 控制器 | 7 个控制器均为占位（返回空数据），请求体 record 与基础校验已搭好 |
| 业务层 | entity / mapper / service / DTO **一行未写** |
| 数据库 | 13 张表结构完整：用户域 2、商品域 5、交易域 5、管理 1 |

数据库设计要点（实现时必须遵守）：

- 无物理外键，关联完整性由应用层保证；
- 金额一律 DECIMAL，接口层用字符串传输；
- 核心表逻辑删除（`deleted`），订单/明细/评价创建后不可变；
- 订单保存商品、规格、图片、收货地址快照；
- 防超卖靠 `t_sku.stock >= ?` 条件更新 + `stock_version` 乐观锁；
- 唯一约束支撑业务：`uk_user_sku`（加购累加）、`uk_order_item_id`（一明细一评价）、`uk_order_no`/`uk_payment_no`（幂等）。

## 二、开工前问题清单（阶段 0 必须处理）

1. pom 缺 JWT 依赖；application.yml 配了 Redis 但 pom 没有 redis starter（refresh token、Idempotency-Key 幂等都要用）。
2. MyBatis-Plus 3.5.9 分页插件已拆分，需额外引入 `mybatis-plus-jsqlparser`，否则分页插件不生效。
3. 未配置：分页插件、乐观锁插件、逻辑删除全局映射（`deleted` 字段）、创建/更新时间自动填充。
4. 安全层只有路由边界：无 `BCryptPasswordEncoder`、无 JWT 过滤器、无当前用户上下文，`httpBasic` 是占位。
5. `GlobalExceptionHandler` 吞异常不打日志；`AccessDeniedException` 会被兜底成 `50000`（应为 40300），无 40100 映射。
6. 接口缺口：`/categories/tree`、`/brands`、`/products/{id}/reviews` 无控制器；管理端缺 `/admin/auth/login`、商品增改、SKU 管理、订单详情、分类管理。
7. 杂项：README 写 `sql/01_schema.sql` 实际在 `docs/`；无种子数据 SQL（管理员账号、示例商品）；openapi.yaml 缺管理端多个路径；AuthController 的 register 复用 LoginRequest（缺 nickname/phone/email）。

## 三、分阶段实施计划

### 阶段 0：基础设施补齐（约半天）

- [ ] pom 补依赖：`jjwt`（0.12.x，api/impl/jackson 三件）、`spring-boot-starter-data-redis`、`mybatis-plus-jsqlparser`
- [ ] MyBatis-Plus 配置类：`PaginationInnerInterceptor`（分页）+ `OptimisticLockerInnerInterceptor`（乐观锁）+ 逻辑删除全局配置 + `MetaObjectHandler` 时间自动填充
- [ ] application.yml 补 mybatis-plus 逻辑删除映射；确认 Redis 连接可用
- [ ] 安全基础：`BCryptPasswordEncoder` Bean、JWT 工具类（签发/校验 access + refresh）、`JwtAuthenticationFilter`、SecurityConfig 接入过滤器并替换 httpBasic 占位
- [ ] 认证失败/无权限返回 40100/40300（AuthenticationEntryPoint + AccessDeniedHandler）
- [ ] `CurrentUser` 工具：从 SecurityContextHolder 取当前 userId（控制器统一入口）
- [ ] `GlobalExceptionHandler` 补日志（含 traceId）+ 40100/40300/40400 映射
- [ ] 建 13 张表的 entity（`@TableLogic`、`@Version` 注解齐全）+ mapper 骨架
- [ ] 修 README 的 schema 路径；写种子数据 SQL（管理员账号 BCrypt 密码、分类/品牌/商品/SKU 示例）
- [ ] AuthController.register 请求体补 nickname/phone/email 字段

**回归点**：服务能启动连上 MySQL/Redis，公开接口返回统一响应结构，受保护接口未带 Token 返回 40100。

### 阶段 1：用户与认证（约 1 天）

- [ ] `POST /auth/register`：用户名/手机号唯一校验，BCrypt 入库
- [ ] `POST /auth/login`：校验密码与状态，签发 access + refresh token
- [ ] `POST /auth/refresh`：refresh token 换新 access token（Redis 存储校验）
- [ ] `GET/PUT /users/me`：资料读取与修改
- [ ] 地址 CRUD：增/改/删/列表（默认地址优先排序）；改删必须校验归属（user_id）
- [ ] 新增地址 `isDefault=1` 时事务内清除旧默认；`PUT /addresses/{id}/default` 设置默认

**回归点**：注册→登录→带 Token 查资料/地址全链路；用 A 用户 Token 改 B 用户地址返回 40300。

### 阶段 2：商品浏览（约 1 天，全公开接口）

- [ ] `GET /categories/tree`：启用分类按 `parent_id` 建三级树
- [ ] `GET /brands`：品牌分页
- [ ] `GET /products`：keyword/categoryId/brandId/minPrice/maxPrice + 5 种排序（default/price_asc/price_desc/sales/newest）；只返回上架未删除；价格用 `price_min/price_max` 冗余字段
- [ ] `GET /products/{id}`：详情 = SPU + 启用 SKU 列表 + 相册 + 评价摘要（均分/数量）
- [ ] `GET /products/{id}/reviews`：评价分页，按星级筛选，仅显示状态

**回归点**：空库走种子数据能完成分类树 → 商品列表 → 详情 → 评价的浏览链路。

### 阶段 3：购物车（约半天）

- [ ] `POST /cart/items`：同 SKU 已存在则累加数量（依赖 `uk_user_sku`，用 `ON DUPLICATE KEY UPDATE` 或先查后改）；校验 SKU 上架且启用
- [ ] `PUT /cart/items/{id}`：改数量/勾选，校验条目归属
- [ ] `DELETE /cart/items/{id}`：删除本人条目
- [ ] `PUT /cart/items/check-all`：批量勾选/取消
- [ ] `GET /cart`：联查 SKU + 商品，实时返回可售状态（下架/禁用/库存不足标记）

**回归点**：同一 SKU 重复加购只有一条记录且数量累加（对应验收项 1）。

### 阶段 4：订单与支付（约 2~3 天，核心难点）

**订单创建（事务，对应验收项 2/4）：**
- [ ] `POST /orders/preview`：按地址 + 勾选购物车试算金额，不扣库存
- [ ] `POST /orders`：Idempotency-Key 幂等（Redis 记录首次结果）→ 地址归属校验 → 查 SKU/商品校验上架 → 条件扣库存（`stock >= quantity`，任一 SKU 失败整单回滚并返回 40900）→ 计算金额（`payAmount = totalAmount + freightAmount - discountAmount`）→ 写订单 + 明细快照 → 删除已结算购物车条目
- [ ] 订单号生成规则（时间戳 + 随机/雪花，满足 `uk_order_no`）

**订单查询与流转（状态机，对应验收项 6）：**
- [ ] `GET /orders`：我的订单分页，按状态筛选
- [ ] `GET /orders/{orderNo}`：详情 = 订单 + 明细快照 + 支付信息，校验归属
- [ ] `POST /orders/{orderNo}/cancel`：仅状态 10，释放库存，写 cancel_time，10→50
- [ ] `POST /orders/{orderNo}/confirm`：仅状态 30，30→40，写 finish_time
- [ ] 状态流转统一封装，非法流转抛 40900，服务端校验不依赖前端

**支付（对应验收项 3）：**
- [ ] `POST /orders/{orderNo}/pay`：仅状态 10；金额从订单读取不接受客户端值；写 `t_payment` 流水返回模拟支付参数
- [ ] `POST /payments/callback`：验签 + 按 `paymentNo` + 金额校验；成功则支付流水置成功、订单 10→20、写 pay_time、累加商品销量；重复成功回调直接返回成功不重复推进
- [ ] （可选）`@Scheduled` 定时任务：超时未支付（如 30 分钟）自动取消并释放库存

**回归点**：并发两个请求买最后 1 件只有一单成功；改价后历史订单仍显示快照金额；回调重复投递订单状态不变。

### 阶段 5：评价（约半天）

- [ ] `POST /orders/{orderNo}/items/{itemId}/review`：校验订单归属 + 订单状态 40 + 明细属于该订单；`uk_order_item_id` 兜底唯一，重复评价返回 40900
- [ ] 请求字段：rating 1~5、content、images、isAnonymous；评价默认显示状态
- [ ] 商品详情/评价列表接口联动新数据（阶段 2 已留好）

**回归点**：已完成订单明细可评价一次，二次评价被拒。

### 阶段 6：管理端（约 1~2 天）

- [ ] `POST /admin/auth/login`：管理员登录，JWT 加角色 claim（与用户 Token 区分，用户 Token 调管理端返回 40300）
- [ ] 商品管理：`GET /admin/products` 分页筛选、`POST /admin/products`（SPU+SKU+相册一个事务，同步算 price_min/max）、`PUT /admin/products/{id}`、`PUT /admin/products/{id}/status` 上下架、`POST /admin/products/{id}/skus`、`PUT /admin/skus/{skuId}` 改价格/库存/状态
- [ ] 订单管理：`GET /admin/orders`（状态/订单号/时间筛选）、`GET /admin/orders/{orderNo}`、`POST /admin/orders/{orderNo}/ship`（仅状态 20，写 express_company/express_no + delivery_time，20→30）
- [ ] 评价审核：`GET /admin/reviews`、`PUT /admin/reviews/{id}/status` 隐藏/显示
- [ ] 分类管理：`GET /admin/categories`、`POST/PUT /admin/categories`
- [ ] （可选）超级管理员（role=2）管理管理员账号

**回归点**：发货后订单进入已发货且写入了物流与时间字段；用户 Token 访问管理端被拒。

### 阶段 7：验收与收尾

- [ ] 单测/集成测试覆盖文档验收清单 6 条（见第四节）
- [ ] 补齐 openapi.yaml 缺失的管理端路径
- [ ] 全链路手工回归：注册 → 浏览 → 加购 → 下单 → 支付 → 发货 → 确认收货 → 评价
- [ ] 清理控制器占位 TODO 与无用代码，统一异常码使用

## 四、验收清单 ↔ 阶段对照（来自接口文档第 6 节）

| # | 验收项 | 依赖阶段 |
|---|---|---|
| 1 | 同用户同 SKU 并发加购最终只有一条记录（`uk_user_sku`） | 阶段 3 |
| 2 | 并发购买最后 1 件库存只有一单成功，失败方 40900，无半订单 | 阶段 4 |
| 3 | 支付回调重复投递不重复改状态、不重复计销量 | 阶段 4 |

| 5 | 用户不能读写他人订单/地址/购物车；用户 Token 不能调管理端 | 阶段 1/4/6 |
| 6 | 状态转换、评价唯一、发货均有服务端校验 | 阶段 4/5/6 |

## 五、约定与提醒

- 事务、库存扣减、支付验签一律放 service 层，控制器只做参数校验和编排（README 明确要求）。
- 客户端传入的 userId、价格、库存、金额全部不可信，一律以服务端查询为准。
- 响应不得暴露 `password_hash`、`deleted`、`stock_version` 等内部字段。
- 金额接口层用字符串、库内用 DECIMAL；时间格式 `yyyy-MM-dd HH:mm:ss`。
- 所有资源按当前登录用户的 user_id 做数据隔离。
